# Optional LM Studio component

The manager keeps a last-confirmed inventory of installed language models while the server is stopped. It labels that list as cached and shows when it was checked. Opening the page does not start the engine; cached entries never count as loaded models. Start the server to refresh the inventory before loading. The private inventory is refreshed when the live list changes or after five minutes of live status checks.

Run `sudo /usr/local/bin/install_lmstudio` after updating DwemerDistro. This installs the reviewed upstream headless engine for `dwemer`. It does not download a selected language model, load one, enable autostart, or change game providers. The upstream bootstrap script is checksum pinned; refresh it only after reviewing a new upstream version.

**First-run path.** Launcher Quick Setup's optional Local AI step offers a dialogue model from `recommended` and an optional decision model from `decisionRecommended` (None by default), with one setup action or **Skip**. Setup installs the engine if needed, downloads the chosen exact files, starts the engine, loads the dialogue model and then the decision model, and only after both are confirmed loaded saves them as the autostart startup pair (None clears a saved decision model). If any step fails, the previous startup pair is kept. Skip changes no LLM Studio settings. Choices saved by older launchers are kept as saved. In the manager, a compact next-step strip follows live status only: install the engine (from the launcher's Components page), choose a model (the existing install dialog, Recommended first), start the server, configure and load, then test. It offers one action at a time and moves back when a model unloads or the server stops, without opening anything or moving focus. A verified download or local import finished on that page selects the model only by the exact `modelKey` the job reports (see below), and only when the load form has no unsaved edits; otherwise the user selects it in Models. Nothing loads automatically. After a test of the selected loaded model passes, newer than its load and not followed by a failed test, **Connect** shows that model's instance ID and the chat URL to copy, with a link to CHIM Quickstart when CHIM is installed. The Dashboard never writes game or server settings and never marks a mod as connected. CHIM Quickstart still warns that loopback URLs cannot reach Windows; the bundled engine is inside WSL, so `127.0.0.1` is correct for it. Changing that warning and adding Local LLM Quickstart support to STOBE and DIALECTIC are separate server follow-ups.

The launcher opens `/Dwemer-Dashboard/lmstudio.php` with a private access key in the URL fragment. The page exchanges it for an eight-hour session and removes the fragment. You can also run `ddistro_lmstudio access` as `dwemer` and paste the key. Do not share the key. Management requests require the session and a CSRF token; `www-data` may invoke only the restricted helper as `dwemer`.

The OpenAI-compatible base URL inside WSL is `http://127.0.0.1:1234/v1`; the full chat URL is `http://127.0.0.1:1234/v1/chat/completions`. Port 1234 is reserved for this component. Stop another server using that port before starting LM Studio. The manager remains usable while inference is stopped. It polls only while visible and never generates on page load.

Presets live in `/etc/dwemerdistro-lmstudio.json`, used by the web manager and by older launcher Quick Setup versions. They pin a Hugging Face repository, revision, file, size and SHA-256. Downloads resume after interruption, verify the whole file, and import through `lms`. Custom inputs accept Hugging Face URLs (for example `https://huggingface.co/Qwen/Qwen2.5-0.5B-Instruct-GGUF@Q4_K_M`) or LM Studio catalog IDs; those use upstream selection and verification. Older launchers list only `models` in Quick Setup; the current launcher sets up a dialogue model from `recommended` and an optional one from `decisionRecommended`. The optional `recommended` list holds pinned community candidates (Light, Balanced, Higher quality) with a tier, purpose, quantization and an optional rough runtime VRAM estimate (`vramGB`, model alone at 4K context); without one the card shows VRAM unknown. They are not game-tested and the estimate is not a fit check. Each also has a `size` label (Small, Medium, Large) that the launcher shows. The optional `decisionRecommended` list holds three pinned Qwen3.5 candidates (Small 2B Q8_0, Medium 4B Q4_K_M, Large 9B Q4_K_M) for an optional second model beside the dialogue model. They have no VRAM estimate, are not tested in-game, and download through the same preset path. The Dashboard does not list them yet. Other pinned alternatives, such as Lumimaid Magnum v4 12B, stay in `models` after the original three so older launchers keep their first default. Cards show Installed only when LM Studio's model folder holds that exact repository path and byte count. System updates replace the catalog only while it matches the last shipped copy; an edited catalog is kept.

**Hugging Face** is the install dialog's second tab. Opening it the first time lists trending public GGUF repositories; nothing is fetched before then. Users can search by name or paste an `https://huggingface.co/<owner>/<name>` URL, and filter by exact creator, parameter range (Hugging Face `num_parameters`), task (any GGUF, text generation or image-text-to-text) and sort (trending, downloads, likes, updated, newest). Gated repositories are left out of results. Results show the parameter count, architecture and context length only when Hugging Face read them from the GGUF header. Show more fetches the next 20 using Hugging Face's cursor; the helper accepts only a cursor token from the browser and rebuilds the fixed endpoint and allowlisted parameters itself. A repository's file list can be narrowed by quantization and download size and sorted by size or name. The helper's read-only `search` and `files` commands call fixed public Hugging Face API endpoints with validated names, a 10-second timeout, bounded response sizes, a ten-minute shared cache keyed by every filter and cursor, and 30 uncached lookups per minute. GGUF chat templates in search responses are discarded, never cached. They never take the job lock, start the engine or download. Only standalone top-level `.gguf` files with LFS size and SHA-256 metadata can be chosen; split parts, `mmproj` vision projectors, `imatrix` calibration data, `mtp-` multi-token prediction companions, subfolder files and gated or private repositories are listed as unavailable. Downloading a chosen file sends only its repository and file name: the job re-reads the file's metadata from Hugging Face, pins the commit revision, size and SHA-256, follows redirects only to Hugging Face hosts, downloads through the preset path into a staging folder named by the expected SHA-256, verifies the whole file and its GGUF metadata (a language architecture and no non-model `general.type`), then imports it. A completed verified download or local import records `modelKey` on the job only when `lms ls --json` lists that exact repository path and byte count as one language model with at most one variant; otherwise the key is omitted rather than guessed. Runtime VRAM for searched files is shown as unknown. No download loads a model.

**Import local model** registers a standalone `.gguf` file that is already on the Windows PC hosting DwemerDistro. Paste its full path (`C:\Models\model.gguf`, or `/mnt/c/Models/model.gguf`); nothing is uploaded from the browser and there is no file browser. The source must be a regular file on a mounted Windows drive (`/mnt/<letter>`), reached without links, shortcuts or junctions anywhere in the path. The helper checks the GGUF header and metadata (version 2 or 3) rather than trusting the extension, and refuses other formats, malformed files and split sets (`-00001-of-0000N` or `split.count` metadata). Metadata parsing is bounded (key length, total metadata size, entry count and time), so a crafted file cannot exhaust memory or hold the worker; real large-vocabulary metadata is well inside these limits. A `split.count` of type UINT16 above 1 marks a shard; a merged model's `split.count` of 0 is accepted, and any other type is refused as malformed. It reads the original without changing it, copies it in bounded chunks with progress into private staging under the manager state folder, and refuses a source that changes during the copy. The model is registered with `lms import --user-repo local/<file name> --yes --hard-link` into the folder `lms` itself uses (`~/.lmstudio-home-pointer`, then `settings.json` `downloadsFolder`), so it occupies one copy of the file. If that folder is on another filesystem, `--copy` is used and the import needs space for two copies, one on each side. Each location needs the file size plus 1 GB free. An existing `local/<file name>` model is never overwritten; rename the file to import another copy. Staging is cleared after each import and after an interrupted one. Before registering, the helper records the staged file identity and destination. If registration fails or is interrupted, it removes the destination only when it is still the same staged file (a hard link). It never uses timestamps or file size alone to infer ownership. A cross-filesystem registration copy, or a replacement file created by another program, is preserved and its path is reported for manual inspection before retrying. An incomplete copy may therefore remain in a custom model folder after failure; inspect it, or rename the source to import under another name. A file that `lms` reports as already present is always preserved. Ollama stores models as managed blobs, not ordinary GGUF files, so they are not imported here; connect CHIM to Ollama instead. Importing does not load the model or change game providers.

Manager state and temporary downloads are under `/home/dwemer/.config/dwemerdistro/lmstudio` (private to `dwemer`). LM Studio manages its own model directory, normally `/home/dwemer/.lmstudio/models`. Updates and reinstall preserve these locations. Turning off autostart or stopping the engine leaves downloads in place. There is deliberately no destructive remove-model or delete-runtime action.

One manager job runs at a time. Load accepts context length, GPU offload percentage and idle TTL. It checks free RAM/VRAM with 2 GB headroom; upstream guardrails still apply and context increases memory needs. Up to two different language models can stay loaded at once, for example a dialogue model and a smaller decision model; loading the same model twice or a third model is refused, so unload one first. Both share RAM/VRAM: the second load is checked against memory left after the first, so size context and GPU offload for the pair. Each loaded model has its own instance ID on the same endpoint for inference clients; the manager only loads, unloads and tests them and does not assign game roles. Loaded models occupy Slot 1 and Slot 2. The helper saves each slot's exact model key in `slots.json` under the manager state folder and reports it as `slots` in status, so slots stay put across polls and reloads whatever order the engine lists models in. Load accepts an optional `slot`; an occupied slot is refused (unload it first, nothing is replaced), and a load without one, such as startup or Quick Setup, takes the lowest free slot. Unloading, an idle unload or stopping the server frees the slot. A model loaded outside the manager takes the lowest free slot. Slots only organise loading: connectors still choose a model by its model ID. Any load or unload clears the last test and load report. The status reports `maxLoaded`; an older helper omits it and the manager keeps the one-model limit.

Advanced loading uses the official Python SDK, pinned to `lmstudio==1.5.0` in the root-owned `/opt/dwemerdistro-lmstudio` virtual environment. Run the component installer again after upgrading an earlier installation to add this dependency. Basic loading remains available without it. Controls include Flash Attention, GPU KV-cache offload, a strict GPU memory cap, keep-in-RAM, mmap, evaluation batch size, seed, K/V cache precision, and RoPE frequency base/scale. Empty fields retain engine defaults. Quantized V cache requires explicitly enabled Flash Attention. The manager displays the engine-reported load configuration; support still depends on the model and runtime.

Save loading defaults separately for each model. They apply in this manager and when DwemerDistro starts an optional selected startup model; they do not rewrite the upstream desktop app's configuration. Autostart remains opt-in. Disabling it preserves defaults and downloaded models. Startup uses the same validation, memory checks, and job lock as manual loading. Settings may also hold an optional `startupDecisionModel` key (empty means none). A settings save changes `startupModel` or `startupDecisionModel` only when the request includes it, so the Dashboard's startup control keeps a saved decision model. Startup loads `startupModel` first, then the decision model, skipping any exact key that is already loaded. It waits up to 360 seconds for each load, the last or only one included, to finish, and fails startup with that job's message if it fails, is interrupted or is replaced.

**Start, Stop and Force stop.** `ddistro_lmstudio start-saved` starts the engine and loads the saved startup models whether or not autostart is on; `autostart` (used at Distro startup) does the same only when autostart is on. Stop is the graceful `stop` job (`lms daemon down`), which waits its turn behind a running job. `ddistro_lmstudio force-stop` is emergency recovery for a hung load, download, test or engine. It does not wait for the job lock: it freezes the job worker recorded in `job.json` (by pid and process start time, through a pidfd, so a reused pid is never signalled), any running `autostart` or `start-saved` helper and their descendants, so nothing can restart the engine, then stops this user's processes whose executable is inside LM Studio's install folders (`~/.lmstudio/llmster`, `~/.lmstudio/bin` and `~/.lmstudio/extensions/backends`, never user files elsewhere in `~/.lmstudio`) and their descendants (SIGTERM, then SIGKILL after 5 seconds) and kills the frozen ones. It never matches processes by name, never touches other users' processes, game servers or other DwemerDistro services, and never removes `job.lock`. While it runs, new jobs and `autostart`/`start-saved` are refused; they hold a shared admission lock only until a worker records itself, so Force stop never waits behind a running job. If LM Studio still answers its API afterwards, Force stop reports failure. It then takes the job lock (waiting at most 10 seconds) and marks only the job that was running when it began as failed; a newer job record is left alone. The current generation, load or download is interrupted; downloads resume on retry. Settings, startup models, loading defaults and downloaded models are kept. A settings save validates the startup pair: each new key must be a language model LM Studio lists now or listed at its last check, a decision model may be set without a dialogue model but must differ from it, and saving never loads or unloads a model.

Test requests require an already loaded model. Temperature, top-P, top-K, min-P, repeat penalty, system prompt, thinking and output limit apply only to the test console, never game connectors. The default output limit is 192 tokens; the maximum is 4,096. Unsupported thinking settings return an error. The last successful bounded response, token counts, speed, time to first token and settings remain available across page reloads. A truncated stream is treated as failure. Saved test presets support browser JSON import/export using the versioned `dwemer-llm-test-v1` format, not the desktop app's preset format. State stays private to `dwemer`; at most 50 model defaults and 10 test presets are stored.

The manager is not a replacement for every desktop feature. CPU-thread overrides, stop strings, parallel-request tuning, speculative decoding, custom prompt templates, runtime switching, LAN/authentication/CORS and JIT-server policy controls are not exposed. The fixed loopback endpoint preserves the shared Quickstart connector contract. Full chat history, documents/RAG and MCP tooling are outside this component's game-serving purpose.

The integration was developed against llmster `0.0.25-1` / lms commit `69d945a`. Core, Dashboard and Launcher changes must ship together. Local model import needs this Core helper and the matching Dashboard manager; an older helper rejects the import action as unknown. Existing onboarding completion stays valid. In-game provider quality and large-model fit must be measured separately from successful component installation.
