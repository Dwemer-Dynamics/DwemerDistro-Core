# Debian 12 to Debian 13 upgrade

`bin/ddistro_trixie_maintenance` upgrades an ordinary DwemerDistro from Debian 12 (Bookworm) to Debian 13 (Trixie). `update.sh` installs it root-only (`0700`) but never runs it. Only the Launcher's OS maintenance runs it, as root, in the order below. While its fence is in place, `start_env` starts no service, `update.sh` exits 75 and `ddistro_pg17_maintenance` exits 75; none of them starts, resumes or cancels the upgrade. The fence stays until `release`, after a successful `verify`.

```
ddistro_trixie_maintenance status    [--json]
ddistro_trixie_maintenance preflight [--json]
ddistro_trixie_maintenance upgrade   --prepare --plan-id ID [--json]
ddistro_trixie_maintenance upgrade   --capture-token TOKEN --recovery-sha256 HEX --recovery-bytes N [--json]
ddistro_trixie_maintenance upgrade   --cancel [--json]
ddistro_trixie_maintenance verify    [--json]
ddistro_trixie_maintenance release   [--json]
```

Exit codes: 0 done; 1 failed (details in `/var/lib/dwemerdistro/trixie-maintenance/maintenance.log`); 2 usage; 3 deferred, nothing changed (JSON `reasons` lists `{code, detail}`); 4 restart the distro and run `verify` again; 75 another maintenance operation holds a lock, nothing changed. With `--json` each command prints one JSON object with `schema: 1`.

## Supported starting point

Everything below is checked by `preflight`; anything else defers with a reason and changes nothing.

- Debian 12 amd64 without foreign architectures, a healthy dpkg database, no held packages, no APT pins other than the stock pin file below, and no existing `policy-rc.d`.
- `/etc/wsl.conf` neither enables systemd (`systemd` absent or `false`, quoted or not) nor runs a `[boot]` command other than exactly `/usr/local/bin/initialize_fresh_distro`. `/etc/wsl.conf` is also one of the guarded files `verify` compares.
- PG17 current: the PG17 journal is `active` with staging cleaned, and `17/dwemer` on disk is the cluster it recorded (`pg_controldata` system identifier equal to the journal's `candidate_id`, and the configuration's `dwemer-maintenance-id` marker naming the journal's staging run; otherwise `pg17-identity`). Exactly the clusters `15/main` (retained, stopped, `start.conf` `disabled`) and `17/dwemer`, with no linked paths, mounts or tablespaces under them.
- Every database uses C, POSIX or C.UTF-8 with the libc provider, and no column uses another collation. Text ordering of other locales can change with glibc 2.36 to 2.41 or ICU 72 to 76, so their indexes need a reviewed `REINDEX`.
- Closed databases (`datallowconn` false): see [Closed databases](#closed-databases). `template0` and the template1 copy that `ensure_postgres_utf8` retained are supported; any other closed database defers.
- APT sources are Debian archive suites, PGDG, the distribution-independent GitHub CLI repository, the stock testing line below, or the [vendor feeds](#vendor-feeds) Core's own installers add, each recognised by its [source identity](#source-identity). Any other third-party or rolling source (another `testing`, `sid`, `forky` line, any deb822 testing stanza, a vendor entry in any other form) defers as unknown.
- PostgreSQL may be serving or, as after a reopened distro, stopped: see [A stopped PG17](#a-stopped-pg17).
- No installed package is newer than every Trixie build of the same name (`apt-ahead-of-trixie`, typically a package taken from testing). APT never downgrades, so such a package would remain a foreign build on Debian 13.

### Source identity

An entry is identified by its exact URI host and path, its suites and components, and its signing policy, never by a substring of the URI. It must name exactly one `http` or `https` URI without credentials, port, query or fragment (a deb822 stanza with a second URI is unknown as a whole), and have no option other than an architecture list that includes `amd64`, a language list (Debian only) and the expected `Signed-By`; `trusted=yes`, `allow-insecure` and any unknown deb822 field leave it unknown.

| Kind | Hosts and path | Suites and components | Signing |
| --- | --- | --- | --- |
| Debian archive | `deb.debian.org`, `ftp.debian.org` or `ftp.<country>.debian.org`, path `/debian` | `bookworm`, `-updates`, `-backports`, `-proposed-updates` (or the `trixie`, `-updates`, `-backports` forms); components `main contrib non-free non-free-firmware` only | no `Signed-By`, or `debian-archive-keyring.gpg`/`.pgp` |
| Debian security | `deb.debian.org` or `security.debian.org`, path `/debian-security` | `bookworm-security` or `trixie-security` only | as above |
| PGDG | `apt.postgresql.org`, path `/pub/repos/apt` | one of `bookworm-pgdg`, `trixie-pgdg`; `main` | `Signed-By` naming one keyring that holds exactly the PGDG key `B97B0AFCAA1A47F044F244A07FCC7D46ACCC4CF8`; an entry without `Signed-By` defers |
| GitHub CLI | exactly `https://cli.github.com/packages` | `stable`; `main`; type `deb` only | `Signed-By` naming one keyring whose primary keys include the current signing key `7F38BBB59D064DBCB3D84D725612B36462313325` and are otherwise only the key it replaced, `2C6106201985B60E6C7AC87323F3D4EA75716059` (GitHub's published keyring, which `repair_github_cli_keyring` keeps current) |

Other mirrors (`mirrors.kernel.org/debian`, a local proxy, `mirror+file:`) are custom feeds and defer as `apt-third-party`.

### GitHub CLI

The official 3.4.5 installer writes `/etc/apt/sources.list.d/github-cli.list`, on fresh and populated images alike, with GitHub's published keyring in `/etc/apt/keyrings/githubcli-archive-keyring.gpg`:

```
deb [arch=amd64 signed-by=/etc/apt/keyrings/githubcli-archive-keyring.gpg] https://cli.github.com/packages stable main
```

The feed is release-neutral (GitHub's `docs/install_linux.md` gives the same line for every Debian release) and carries only `gh`. Its `InRelease` is signed by `7F38…2313325`; `2C61…5716059` expired on 2026-09-06 and stays in GitHub's keyring. The equivalent deb822 stanza (`Types: deb`, `Architectures` including `amd64`, the same `Signed-By`) is recognised too, as is the earlier single-key keyring holding only `7F38…2313325`. Another host, path, scheme, port, credentials or query, `deb-src`, a different suite or component, any option other than the `amd64` architecture list (`trusted=yes`, `allow-insecure`, `lang`), a missing `Signed-By`, several keyrings, or a keyring holding only the retired key or any other key (PGDG's included) defers as `apt-third-party`.

The entry, the keyring and the system pins are never changed: after the upgrade `apt` uses the source exactly as before, and `verify` accepts it next to the Trixie suites. In the rehearsal and the transaction:

- When `gh` is not installed (`ii`), the feed is left out of the private sources, so the upgrade cannot add `gh`.
- When `gh` is installed, the private sources name the feed with a byte-for-byte copy of the installed keyring in the private APT directory. The copy is checked again against the keys above, and a keyring that changed since it was recognised fails preflight. The private preferences pin the feed's origin `cli.github.com` to -1, except `gh` at 500. These pins exist only in the private APT directory, never in `/etc/apt/preferences.d`. APT verifies the feed's signature as for every other private source (`apt-signature` when it fails).
- The installed `gh` is upgraded to the feed's build, which is newer than Debian 13's own `gh`. The feed's `gh` is not reported as `obsolete_kept` or `apt-ahead-of-trixie`; any other name the feed might carry gets no such exemption. The solution is refused (`vendor-package`) when the feed would supply a package other than `gh`, or would add `gh` where it is not installed, and (`vendor-component-removed`) when it removes an installed `gh`.

### The stock testing source

The official 3.4.5 installer leaves this line active in a one-line `.list` file next to the ordinary Bookworm sources and GitHub CLI:

```
deb http://deb.debian.org/debian testing main non-free contrib
```

Only this exact line (whitespace and a trailing comment aside) is recognised; `https`, options, other components, `deb-src` or deb822 variants defer as `apt-third-party`. During the rehearsal its components join the private Trixie sources. When the upgrade persists the sources, the original file is kept in `apt-sources-bookworm/`, the line is replaced by a comment that quotes it, and only components that no active Bookworm (or already rewritten Trixie) main-archive line carries are added as `deb http://deb.debian.org/debian trixie <components>`. With the stock sources, which carry `main contrib non-free non-free-firmware`, nothing is added. `verify` refuses while any active Debian or PGDG entry still names `bookworm*` or a rolling suite (`testing`, `unstable`, `sid`, `experimental`, `forky`).

### The stock pin file

The same installer writes `/etc/apt/preferences.d/stable`:

```
Package: *
Pin: release a=bookworm
Pin-Priority: 900

Package: *
Pin: release a=testing
Pin-Priority: 300
```

It is recognised by meaning, not bytes: field names in any case, whitespace, `#` comments, `Explanation:` lines, `archive=` for `a=` and the order of the two stanzas do not matter. It must be the only entry in `/etc/apt/preferences.d`, a plain file named `stable`, with `/etc/apt/preferences` absent or empty. Any other pin, priority, package pattern, extra stanza or file (ignored extensions included) defers as `apt-preferences`. The rehearsal and the transaction never read system pins. At the cutover, with the sources, the original is kept in `apt-preferences-bookworm/` and the file is replaced by its Debian 13 form: `trixie`, `trixie-updates` and `trixie-security` (by codename, `n=`) at 900, and PostgreSQL packages from PGDG at 950, the same order the rehearsal used. Without that last stanza the release pin would move PostgreSQL 17 from PGDG to Debian's own `postgresql-17` at the next Debian point release. No `testing` or `bookworm` pin remains. `verify` refuses unless preferences are absent or exactly that file. The guarded-configuration digests skip `/etc/apt/sources.list*` and `/etc/apt/preferences*`, which the cutover rewrites on purpose.

### Vendor feeds

`install_cuda_dependencies` adds NVIDIA's CUDA repository through `cuda-keyring`, and `ddistro_reign build` adds Microsoft's .NET feed through `packages-microsoft-prod`. Only these exact Debian 12 entries are recognised, as a one-line or deb822 entry with no options other than an architecture list that includes `amd64`:

```
deb [signed-by=/usr/share/keyrings/cuda-archive-keyring.gpg] https://developer.download.nvidia.com/compute/cuda/repos/debian12/x86_64/ /
deb [arch=amd64,arm64,armhf signed-by=/usr/share/keyrings/microsoft-prod.gpg] https://packages.microsoft.com/debian/12/prod bookworm main
```

Each moves to the vendor's Debian 13 feed (`…/repos/debian13/x86_64/ /`, `…/debian/13/prod trixie main`), signed by a key fetched over HTTPS for that feed and accepted only with its pinned fingerprint. The Debian 12 keyrings are never reused:

| Feed | Key | Fingerprint | Installed as |
|---|---|---|---|
| NVIDIA CUDA | `https://developer.download.nvidia.com/compute/cuda/repos/debian13/x86_64/8793F200.pub` | `02182E60104FCDC26EAE1B8597A5D4CB8793F200` | `/etc/apt/keyrings/dwemerdistro-nvidia-cuda-debian13.gpg` |
| Microsoft | `https://packages.microsoft.com/keys/microsoft-2025.asc` | `AA86F75E427A19DD33346403EE4D7792F748182B` | `/etc/apt/keyrings/dwemerdistro-microsoft-debian13.gpg` |

The rehearsal includes these feeds and the same pins the cutover writes to `/etc/apt/preferences.d/dwemerdistro-vendors` (read before `stable`, so its rules come before the 900 Trixie release pin). Each feed's origin is pinned to -1, except for versioned user-space packages at 500: CUDA toolkit components and libraries such as `cuda-cudart-12-8`, `cuda-nvcc-12-8`, `libcublas-12-8`, `libcufft-12-8` and the `cuda-toolkit-*-config-common` packages, and the .NET `dotnet-*`, `aspnetcore-*` and `netstandard-targeting-pack-*` packages. A vendor feed therefore never supplies `cuda-drivers*`, `cuda-compat-*`, `cuda-runtime-*` or other metapackages, `nvidia-*`, `libnvidia-*`, kernel modules, `cuda-keyring` or `packages-microsoft-prod`, which keep their installed builds. Installed packages a feed carries are not reported as `obsolete_kept` or `apt-ahead-of-trixie`. The solution is refused when:

- a package whose planned version a vendor feed carries (read from the private `apt-cache policy`, not from the label in the plan) is not one of those components (`vendor-package`),
- it would add a CUDA series or .NET version that is not installed, for example `cuda-nvcc-13-0` next to an installed 12.8 (`vendor-series`),
- it removes an installed component, manual or not, such as `cuda-cudart-12-8` (`vendor-component-removed`).

`upgrade --prepare` also records `/usr/local/cuda*` (the CUDA homes such as `/usr/local/cuda-12.8` and the alternatives links that select them), and `verify` refuses if any changed (`cuda-layout`). `/var/lib/dwemerdistro/cuda-selection.env` is one of the guarded files. A vendor entry already in its Debian 13 form on Debian 12 defers as `apt-third-party`; after the cutover, `verify` refuses while a vendor entry still names its Debian 12 feed, or while the vendor pin file is missing or different.

On Debian 13 the installers keep to the matching feed: `install_cuda_dependencies` uses the `debian13` feed (installing `cuda-keyring` only when no CUDA feed for the release is configured) and refuses when only another release's CUDA feed is configured. `ddistro_reign build` counts only active (uncommented) source lines: it installs the .NET SDK from a configured `debian/13` feed (the one this upgrade migrated, under the vendor pins), and refuses a feed for another release. On a clean Debian 13 system without a Microsoft feed it downloads Microsoft's documented configuration package `https://packages.microsoft.com/config/debian/13/packages-microsoft-prod.deb` and installs it only when its `Package` is `packages-microsoft-prod`, every key it ships under `usr/share/keyrings`, `etc/apt/keyrings` or `etc/apt/trusted.gpg.d` is exactly the pinned Microsoft key `AA86F75E427A19DD33346403EE4D7792F748182B`, and an active source it ships names `https://packages.microsoft.com/debian/13/prod`; afterwards that feed must be active. It installs `gpg` first when missing. The Debian 12 path is unchanged. The vendor pins admit `dotnet-host` with or without a `-<major>.<minor>` suffix and `netstandard-targeting-pack-<x.y>[-<x.y>]`, so either naming of the .NET host packages installs.

### A stopped PG17

A reopened distro has not run `start_env` yet, so PG17 is stopped and its socket absent. `preflight` and `upgrade --prepare` support that state without starting PostgreSQL publicly:

- First a private server an interrupted run left is stopped. Then, read-only: `17/dwemer` must be the journaled cluster (see [Supported starting point](#supported-starting-point)), and PG15 must not run (`pg15-guard`).
- If PG17 runs, or anything accepts a connection on `/var/run/postgresql/.s.PGSQL.5432` (the probe connects and closes without sending anything), that server is inspected there and must report version 17 and data directory `/var/lib/postgresql/17/dwemer`. A wrong live server is still refused (exit 1).
- Otherwise PG17 is provably stopped: its `pg_control` state must be a primary's (`shut down`, or `in production`/`in crash recovery` after an abrupt stop; anything else is `pg17-identity`). `preflight` then starts it only on the private peer socket, inventories it from shared catalogs (closed databases are not opened, as on the public socket), and stops it again. `upgrade --prepare` skips the public pre-check and fences first; its private inspection (see step 3) covers the same checks. It records PG17 as not running, so a `prepare` that defers after fencing, a `cancel` or a `release` restores the original `start.conf` and starts no cluster (see [Restoring what ran at the fence](#restoring-what-ran-at-the-fence)); the Launcher starts the distro normally, which starts the services `/etc/dwemerdistro_services.conf` selects.

`ddistro_pg17_maintenance status` (and `auto`, `upgrade` for an uncleaned journal and `cleanup-staging`) accepts the same state with its existing replies: for an `active` journal, when neither PG17 runs nor anything accepts on the application socket, it reports `current` (or `cleanup-needed`) only when `17/dwemer`'s system identifier is the journal's `candidate_id`, its configuration carries the journal's marker, its `pg_control` state is a primary's, its `start.conf` is `auto` or `manual`, and PG15 is stopped with `start.conf` `disabled`; otherwise it exits 1 with nothing changed. It starts nothing and sends no SQL in that case. A running PG17, or anything on the socket, is still checked by SQL as before. The `rolled-back` and journal-less replies still need PG15 serving.

### Closed databases

After the merged PG17 migration a stock install has two closed databases: `template0` and `ddistro_template1_before_utf8_<UTC timestamp>` (C locale, UTF8), the original empty `template1` that `ensure_postgres_utf8` renamed and closed. The upgrade never opens a closed database on the public server, never changes its `ALLOW_CONNECTIONS`, `IS_TEMPLATE`, owner or ACL, never grants anything, and never drops it.

- `template0` is skipped as built in only while it is still a template (`datistemplate` true).
- The retained template is recognised only by every one of these shared-catalog traits, read without connecting to it: a name `ensure_postgres_utf8` gives (`ddistro_template1_before_utf8_` and 14 digits), not a template, no connection limit, owned by the bootstrap superuser, ACL grantees only `PUBLIC` and the owner, the default tablespace, no per-database role settings, no `pg_shdepend` entries (no object owned by or granted to another role), the libc C or POSIX locale, at most 64 MiB on disk, and no unfinished `ensure_postgres_utf8` change (`/var/lib/dwemerdistro/postgres-template-5432.pending` absent). A database that misses any trait defers as `pg-closed-database` with the missing traits listed. The name alone is never enough.
- Its contents are inspected only on the private PG17 server (peer socket for `postgres`, no TCP, autovacuum off): in `upgrade --prepare` after PG17 stopped, and again in `verify`. The helper first journals the name in `/var/lib/dwemerdistro/trixie-maintenance/closed-open.json`, sets `ALLOW_CONNECTIONS true`, reads its extensions, non-default column collations and object count (the same test `ensure_postgres_utf8` applied before retaining it), then sets `ALLOW_CONNECTIONS false` and removes the journal. Every private start closes the databases a left-over journal names before it does anything else, and `cancel` does so before it removes the fence, so an interrupted inspection never reaches clients. If the database holds anything beyond `plpgsql`, `prepare` lifts its own fence, starts again what it stopped and defers.
- The fence record compares, for every database: oid, name, template flag, `datallowconn`, connection limit, owner, ACL shape, tablespace, settings and shared dependencies, plus locale and encoding; and for every inspected database its extensions and, for the retained template, its object count. Sizes and collation versions are not compared.
- Installed PHP packages belong to PHP 8.2 only, each has a PHP 8.4 counterpart in Trixie, and no PHP extension module was installed outside a package.
- Each Python virtual environment either uses an interpreter of its own, or Debian's Python 3.11. One built on another Debian interpreter defers.
- No shared object in a venv asks for an executable stack, other than the stock LocalWhisper CTranslate2 library below (see [Executable-stack libraries](#executable-stack-libraries)).
- `/etc/start_env` is the current one, which honours the fence (Update Distro first).

### Executable-stack libraries

glibc 2.41 (Debian 13) no longer makes the stack executable when `dlopen` loads a shared object whose `PT_GNU_STACK` header asks for one (`PF_X`), so importing it fails with `cannot enable executable stack as shared object requires: Invalid argument`. The stock LocalWhisper venv has such a file: CTranslate2 4.4.0's bundled `/home/dwemer/python-stt/lib/python3.11/site-packages/ctranslate2.libs/libctranslate2-d3638643.so.4.4.0` (71690457 bytes, SHA-256 `3fdf882ba5de43ac05bace3538dd980715848deec75b563d6e7fa6a79c3bdd78`, `GNU_STACK RWE`). It loads on Bookworm and fails on Trixie. Executable stacks are never enabled (no `glibc.rtld.execstack` tunable, no other system setting), and nothing is reinstalled.

`preflight` reads the `PT_GNU_STACK` header of every `.so` file in every venv it checks (at most 50000 per venv; more defers). Any file asking for an executable stack defers as `venv-execstack`, except exactly that file, and only while all of these hold: it is in `/home/dwemer/python-stt`, a retained Python 3.11 venv; it and the wheel's `ctranslate2-4.4.0.dist-info/RECORD` are regular files reached through no symlink; both belong to the venv's owner; its size and digest are the stock ones; and `RECORD` lists it once with that digest and size. A private build, another venv or path, or an edited `RECORD` defers and is never changed.

Before the solver runs, and before anything is written, `preflight` copies the `ctranslate2` and `ctranslate2.libs` directories to a scratch directory under `/var/tmp`, clears `PF_X` in that one program header of the copy (the 4-byte change `patchelf --clear-execstack` makes; the digest it must give is computed and planned), and runs the venv's own `bin/python -I` as the venv's owner on the copy. The probe must import `ctranslate2` from the copy, have mapped the copy's library, run with a non-executable stack, list the CPU compute types and round-trip a `StorageView`. When a converted Whisper model (`model.bin` with `config.json`) is on disk, one is also loaded: the model LocalWhisper's `config.yaml` (a link to one of its `config-*.yaml`, inside `/home/dwemer/remote-faster-whisper`) selects, resolved as faster-whisper does (a directory relative to LocalWhisper, such as `numbat-base-skyrim-en`, otherwise the `refs/main` snapshot of that size downloaded into `model_cache_dir`, `/home/dwemer/remote-faster-whisper/models/` in the stock configurations); without one, the smallest under `/home/dwemer/remote-faster-whisper/models`, then `/home/dwemer/.cache/huggingface/hub`. The probe loads it on the CPU and runs its encoder and a decoder step (`detect_language` on 30 s of silent features); the probe then reports `speech`, otherwise `import`. A failure or a 900-second timeout defers as `venv-execstack` with the error. The scratch directory is removed. The planned fix (paths, offset, stock and cleared digests, old and new `RECORD` lines, probe level) is part of `plan.json`, the plan id and the journal; `preflight --json` lists it as `venv_execstack`.

`upgrade --prepare` defers (`plan`) when the file or its `RECORD` line changed since preflight, and the transaction returns to `fenced` (`plan-changed`) when they changed before dpkg runs. After the package transaction (step 6, after the venv interpreter links), the library is rewritten as a new file in its directory with the same owner, group and mode, checked against the planned digest and renamed over the original; then only its `RECORD` line is replaced with the new digest (same size), keeping every other byte and the file's owner and mode. Before either is written, both are checked again: each a regular file inside the venv, reached through no symlink and held by the venv's owner, the library with the stock or cleared digest and `RECORD` holding exactly one of the two lines (the cleared line beside a stock library does not count); the library is checked once more just before the rename. A rerun keeps a file or line already in its planned form and stops with both untouched (the upgrade stays `interrupted`; restore the recovery copy) if either changed in any other way. Only the temporary file the current run created is removed when that run fails; any other file beside the library, including a temporary file an interrupted run left, is kept (and named in the log) for review. `verify` requires the planned file and `RECORD` line and runs the same probe on the venv itself under Debian 13; it fails (`venv-execstack`) when the import fails, or when preflight ran a `speech` probe and only an `import` probe runs now.

The fix covers the bits on disk at the upgrade. LocalWhisper's own installer pins `ctranslate2==4.4.0`; reinstalling that wheel into `python-stt` after the upgrade brings back the stock library with its executable-stack request, which Debian 13 refuses to import, and nothing in core re-applies the fix.

## The solver rehearsal

`preflight` works in a private APT directory (`/var/lib/dwemerdistro/trixie-maintenance/apt`). The system's sources, lists, pins and caches are not read or changed. It configures `trixie`, `trixie-updates` and `trixie-security` from `deb.debian.org` signed by the installed `debian-archive-keyring`, and `trixie-pgdg` signed by the PGDG key, accepted only with fingerprint `B97B0AFCAA1A47F044F244A07FCC7D46ACCC4CF8` (taken from `postgresql-common` when present, otherwise downloaded over HTTPS). Debian components are those the existing Debian sources use. Lists that fail to verify defer as `apt-signature`; there is no unsigned fallback.

PostgreSQL packages (`postgresql*`, `libpq5`) are pinned to PGDG at 600; every other PGDG package is pinned at 100. PGDG Trixie builds are newer than the installed PGDG Bookworm and Debian Bookworm builds, so PG15, PG17, `postgresql-17-pgvector` and their clients are rebuilt for Trixie without a downgrade.

One `full-upgrade` is solved with recommends off: every installed `php8.2-*` and `libapache2-mod-php8.2` package is replaced by its `8.4` counterpart in the same transaction, and `libicu76` is added when Reign is installed. The solution is downloaded, then refused when it:

- removes one of PostgreSQL, `libpq5`, Apache, `sudo`, `ca-certificates`, `git`, `python3`, `python3-venv`, `openssl`, `curl` or `debian-archive-keyring`, other than the requested PHP 8.2 packages,
- removes a manually installed package, unless it is a Debian 13 transition shown below,
- downgrades a package, keeps one back, leaves an installed package newer than Trixie (`apt-ahead-of-trixie`), or leaves an installed PostgreSQL package without a Trixie build that is not older,
- removes `python3.11` while a venv uses it, or removes the only package shipping a system library that a venv's compiled module loads (bundled wheel libraries are excluded, and a renamed `t64` package that ships the same soname counts as kept),
- newly installs a package that ships an init script or systemd service, other than the PHP 8.4 counterpart of an installed PHP 8.2 package (`php8.4-fpm` for `php8.2-fpm`; it starts only when the Launcher starts services after `release`),
- drops an installed extension version: when a new PostgreSQL package ships an extension's control file, it must also ship a script for every installed version of that extension (so pgvector cannot go back),
- installs or upgrades a package from anywhere other than the Debian archive or its security archive, except the PGDG-pinned PostgreSQL packages from `trixie-pgdg` (`apt-origin`) and the vendor components checked under [Vendor feeds](#vendor-feeds),
- needs more free space on `/` and `/var` than the download, the growth APT reports, and a 2 GiB margin.

Three bounded changes to the request are made before checking, each at most once, then the solution is solved again. All are kept in the plan, so the transaction solves the same request:

- With no installed package providing `mail-transport-agent`, a solution that newly installs a mail server, `exim4-daemon-light`, `exim4-daemon-heavy`, `postfix` or `msmtp-mta` (which ships `msmtpd.service`), because Debian 13's `gpg-wks-server` depends on a mail transport, gets `esmtp-run` requested instead. `esmtp` and `esmtp-run` ship no service and only relay when called. The new-service check still applies to it. An installed transport is never replaced.
- Installed packages from the stock `nvidia-cuda-toolkit` source that APT keeps back (for example `libcupti-dev` once the relay is requested) are requested explicitly, so they go to their Trixie build. Every other kept-back package still defers, and the removal, downgrade and hold checks apply to the new solution.
- For each installed, manually installed stock CUDA profiling library the solution removes without a successor (for example `libaccinj64-11.8` and `libcuinj64-11.8`), the one Trixie package of the same library and a newer series from `nvidia-cuda-toolkit` is requested (`libaccinj64-12.4`, `libcuinj64-12.4`). Nothing is requested for a library that is not installed, and none when the Trixie lists offer no or several such packages; the removal then still defers. The checks for users of the old soname apply as below.

On the reference laptop (ASUS, pass 3) the signed simulation with `esmtp-run`, `libaccinj64-12.4`, `libcuinj64-12.4` and `libcupti-dev` requested solves 782 upgrades, 187 new packages and 65 removals with nothing held.

Packages requested only for these reasons keep (or, for the relay, get) the automatic mark after the transaction.

### NVIDIA kernel module on the WSL kernel

The official image has Debian's `dkms`, `nvidia-kernel-dkms`, `libcuda1` and `nvidia-smi` (535) installed manually, with the module built and installed for its Debian kernel `6.1.0-33-amd64`. The Trixie `nvidia-kernel-dkms` 550 postinst (Debian's `common.postinst`, with `autoinstall_all_kernels`) builds the module for every kernel whose `/lib/modules/<release>/build/include` exists. On the ASUS laptop that includes the running WSL kernel `6.18.58.1-microsoft-standard-WSL2`, the build fails there (exit 10), and dpkg stops after the recovery copy. Under WSL the GPU is reached through the host's `/usr/lib/wsl/lib`; no NVIDIA module loads on the WSL kernel.

The package is upgraded, not removed. Its manual mark, holds (which defer anyway), the CUDA and NVIDIA user space, and the module builds for every other kernel stay as Debian handles them. On a stock WSL2 kernel (`/proc/sys/kernel/osrelease` of the form `6.18.58.1-microsoft-standard-WSL2`, with `/usr/lib/wsl/lib` present), when the solution upgrades or installs `nvidia-kernel-dkms`:

- `preflight` reads the DKMS name and version from the downloaded package's postinst (`DKMS_NAME=nvidia-current`, `DKMS_VERSION=550.163.01`) and requires `/usr/src/<name>-<version>/dkms.conf` in it. It plans one override, `/etc/dkms/nvidia-current-550.163.01-<WSL release>.conf`, which DKMS (3.0 and 3.2, dkms(8)) reads after the packaged `dkms.conf`, containing a comment and `BUILD_EXCLUSIVE_KERNEL="^$"`. DKMS then skips that one module version on that one kernel with exit 77, which `common.postinst` and `dkms autoinstall` pass over. Other kernels and other versions are not affected. Preflight writes nothing; the planned override is part of `plan.json`, the plan id and the journal.
- It defers before the recovery copy (`nvidia-kernel-module`) when the package's DKMS identity cannot be read; when `/etc/dkms` is a symlink or not a directory; when something already exists at the override path, a symlink included, unless it is a regular file with exactly the planned content; or when an override dkms 3.2 reads later exists (`<name>-<version>-<release>-x86_64.conf`, `<name>--<release>.conf`, `<name>--<release>-x86_64.conf`, dangling links included), because that file would decide instead. Overrides read earlier (`<name>.conf`, `<name>-<version>.conf`) are left alone: the planned file only narrows the build further, for this kernel.
- The upgrade (step 6) solves and downloads again, then derives the override from the refreshed package and running kernel. A different module version, kernel or blocker returns `plan-changed` before any package changes. It then writes the file atomically (`0644`), or keeps it when it is already there with that content, before dpkg starts. A resumed transaction (step `dpkg`) re-creates a missing override, and stops before dpkg if the file was changed or a later override appeared. `cancel`, and a transaction that returns to `fenced`, remove the file only while it still has exactly that content.
- The file is kept after the upgrade, so `dpkg-reconfigure nvidia-kernel-dkms` and `dkms autoinstall` keep skipping the WSL kernel. `verify` refuses (`nvidia-kernel-module`) while it is missing, changed or overridden.

Isolated lab evidence (`DwemerPg17MigrationLab`, private mount namespace over `/etc`, `/usr` and `/var`): real `dpkg -i` of Debian's `dkms` 3.0.10-8+deb12u1 and `nvidia-kernel-dkms` 535.261.03-1, the 535 module installed for a scratch `6.1.0-33-amd64`, then a scratch `6.18.58.1-microsoft-standard-WSL2` with `build/include`. A stub `make` stands in for the compiler: it fails for the WSL kernel and produces the five modules for any other. Without the override, upgrading to `dkms` 3.2.2-1~deb13u1 and `nvidia-kernel-dkms` 550.163.01-2 reproduced the laptop failure (exit status 10, `iF`). With the override the helper wrote, the same upgrade ended `ii`, with 550 installed for `6.1.0-33-amd64` and the WSL build skipped without calling `make`. `dpkg-reconfigure nvidia-kernel-dkms` and `dkms autoinstall -k <WSL>` passed afterwards. A later `nvidia-current--<WSL>.conf` won in real dkms 3.2.2 (the build ran and failed), and the helper refused it. dkms 3.0.10 also skipped the WSL kernel with exit 77.

Debian 13 transitions a manually installed package may take:

- Renames (the `t64` libraries such as `libssl3` to `libssl3t64`, and similar): a package newly installed by the same solution declares `Replaces` on the old name and either `Provides` it or ships every shared library file name the old package shipped. This is read from the downloaded, signed `.deb` files, never from names. The successor is marked manual after the transaction, and preflight lists the pairs as `transitions`. A so-bumped library without such a successor (for example `libzip4` to `libzip5`) still defers. When a manual removal is not explained otherwise, the relations of the upgraded packages are read too, so an upgraded package that declares `Replaces` and `Provides` on the removed name takes it over. One verified packaging transition needs `Provides` alone: Bookworm's `libtinfo-dev` ships nothing outside `/usr/share/doc` and depends on `libncurses-dev`, whose Trixie build `Provides: libtinfo-dev` while its `Replaces` names only `ncurses-dev`. `libncurses-dev` takes over `libtinfo-dev` only while the installed `libtinfo-dev`'s file list (`dpkg -L`) holds nothing but `/usr/share/doc`; no other pair is accepted this way.
- Stock CUDA profiling and injection libraries (`libcupti<series>`, `libcuinj64-<series>`, `libaccinj64-<series>` from `nvidia-cuda-toolkit`, such as `libcupti11.8`): accepted when the Trixie lists no longer carry the name, the same solution installs or upgrades the same library of a newer CUDA series from Debian (`libcupti12`, `libcuinj64-12.4`), no venv loads the old soname, and no ELF file under `/usr/local` or `/opt` loads it (`cuda-library-users`; more than 50000 files to read defers too). Successors are marked manual and listed in `transitions`. A library without such a successor still defers.
- Drops without successor, accepted only when the Trixie lists carry no package of that name: `python3-distutils` (Python 3.12 removed distutils), `python3-lib2to3` (Python 3.13 removed lib2to3) , `libcurl3-nss` (curl removed NSS) and `python3.11-venv` (no Python 3.11 in Debian 13; accepted only while the solution keeps `python3.11`). Preflight lists them as `dropped`. Existing Python 3.11 venvs keep running on the retained interpreter; creating new Python 3.11 venvs with bundled pip is no longer supported by a package. Retained Python 3.11 venvs lose the system `distutils` and `lib2to3`; setuptools' own `distutils` shim keeps working.

The signed Trixie lists provide `php8.4-*` counterparts of the stock PHP 8.2 packages, including `php8.4-mcrypt`, and PGDG `trixie-pgdg` builds of `postgresql-15`, `postgresql-17` and `postgresql-17-pgvector`. Packages without any Trixie build (for example `libicu72`, `python3.11`, or Bullseye leftovers such as `python3.9`) are reported as `obsolete_kept`; they stay installed and nothing autoremoves them. `preflight` writes `plan.json` and prints its `plan_id`.

### Preflight result

`preflight --json` on `ready` prints, besides `plan_id`, `counts`, `removals`, `installs`, `php`, `obsolete_kept`, `transitions`, `dropped`, `retained_databases` and `venvs`:

- `used_bytes`: an upper bound, in bytes and always above zero, of the root filesystem's file data, for sizing the host export. It is the larger of (a) the filesystem's allocated blocks from `statvfs("/")` (`(f_blocks - f_bfree) * f_frsize`, which includes metadata and the journal) and (b) a walk of the root filesystem only (other mounts such as `/mnt/c`, `/proc` or `/usr/lib/wsl` are excluded): each inode's data once at the larger of its apparent and allocated size, rounded up to 512 bytes, so sparse files count in full as an uncompressed tar stores them, plus 1536 bytes of header room per entry and 20 KiB for the archive end. It is measured after the rehearsal, so it includes the downloaded archives and `plan.json`. It is not the size of a VHDX, whose unreclaimed blocks the host must measure itself.
- `upgrade_bytes`: an upper bound, in bytes and always above zero, of the working space the upgrade needs inside the distro beyond its current files: the size of every archive in the plan (APT's `Need to get A/B` total B, counted even though preflight already downloaded them into the private cache), plus APT's net growth when positive, plus the 2 GiB margin for dpkg's unpack copies, logs and the private lists.

### Status result

`status --json` also reports `codename` (`VERSION_CODENAME` from `/etc/os-release`, for example `bookworm` or `trixie`; empty when unknown) and `instance_id`. `instance_id` is `ddi1-` followed by the first 40 hex digits of SHA-256 over a fixed domain string and `/etc/machine-id`; the machine id itself is not disclosed. It stays the same for the life of an install, and is `null` when `/etc/machine-id` is missing, all zeros or not 32 hex digits, or while the fresh-image marker shows that `initialize_fresh_distro` has not yet given the image its own machine id. A recovery copy or an export imported elsewhere keeps the same machine id, so `instance_id` only corroborates the host's WSL registration (distribution GUID and base path); it never identifies an install on its own.

## Host protocol

1. `status --json` reports `state`: `needed`, `deferred` (with reasons), `unsupported`, `not-needed` (already Debian 13), `fence-incomplete`, `fenced`, `interrupted`, `upgraded`, `verified`, `current` or `failed`, and `next`. It only reads files (the journals and, through `pg_controldata`, PG17's control file for the identity check): no lock, no network, no PostgreSQL connection, no service. `needed` does not prove the live state; `preflight` does.
2. With the supported Windows games idle, `preflight --json`. On `ready`, keep `plan_id`.
3. `upgrade --prepare --plan-id ID` refuses a stale plan (over 7 days, or any dpkg change since). It records the explicit PHP 8.2 settings and modules, the digests of private configuration (user-modified conffiles, `/etc/postgresql`, `/etc/dwemer`, `/etc/sudoers.d`, Apache sites, `/etc/dwemerdistro_services.conf`, `/etc/start_env`, `/etc/wsl.conf`, the PG17 journal) and which writers ran. Symlinks in those directories are recorded by target and resolved content. A file there that dpkg lists as exactly one unflagged conffile of one package, reached through no symlink and still matching dpkg's md5, is recorded as that vendor conffile instead: `verify` accepts it unchanged, or replaced by dpkg with the conffile of a newer version of the same package (a new md5 in dpkg's record that the file matches). Debian 13 ships new stock `default-ssl.conf` and `sudoers.d/README` this way. Anything else (edited before or after, missing, renamed, moved to another package, symlinked, flagged `obsolete` or `remove-on-upgrade`, or with an unrecognised dpkg record) counts as changed. Core's cluster configuration and sudo policy are not dpkg conffiles and keep their exact digests. It then writes `/etc/dwemer/trixie-upgrade.fence`, stops Apache and PHP-FPM if they run, sets `17/dwemer` to `manual` and stops PG17 cleanly if it runs (see [A stopped PG17](#a-stopped-pg17)). On the private server it records the PG17 roles, global role settings (`ALTER ROLE … SET`), database identities, extension versions and the retained template's contents (see [Closed databases](#closed-databases)), stops PG17 again, records its `pg_control` seal and prints `capture_token`.
4. The Launcher terminates the distro (`wsl --terminate`), exports it, and verifies the export: it must restore, and its `/var/lib/dwemerdistro/trixie-maintenance/state.json` must hold the same `token` with phase `fenced`. Core never sees, creates or deletes the export. A failure here: start the distro and run `upgrade --cancel`.
5. Start the distro without running `start_env`, then `upgrade --capture-token TOKEN --recovery-sha256 HEX --recovery-bytes N`. Core refuses unless the token matches, the fence file is present, PG15 and PG17 are stopped, PG17's seal is unchanged, Apache and PHP-FPM are stopped and dpkg is unchanged. The token proves the export was taken inside the fence; the digest and size are recorded for the record only.
6. Core refreshes the private lists and solves again. A different removal set returns to `fenced` with exit 3 (`plan-changed`): cancel and preflight again. Otherwise it downloads, then installs a `policy-rc.d` that refuses every service start or stop and runs the transaction with `--force-confold --force-confdef`, `UCF_FORCE_CONFFOLD=1` and noninteractive frontends. Modified conffiles, ucf-managed `php.ini` files and every PHP 8.2 configuration (removed, not purged) stay as they are. Afterwards it switches Apache to `php8.4`, writes `/etc/php/8.4/<sapi>/conf.d/99-dwemerdistro-from-php8.2.ini` with the PHP 8.2 settings the user set explicitly that PHP 8.4 knows and does not already have (`session.sid_length`, `session.sid_bits_per_character` and `extension_dir` are not carried, nor any setting PHP 8.4 warns about at startup), points Python 3.11 venvs whose `bin/python3` links to `/usr/bin/python3` at `/usr/bin/python3.11` and marks that interpreter manual, clears the planned executable-stack request of the stock CTranslate2 library (see [Executable-stack libraries](#executable-stack-libraries)), marks the successors of manually installed renamed packages manual, replaces the stock pin file by its Debian 13 form (original kept in `apt-preferences-bookworm/`) and writes the vendor pins, installs the verified Debian 13 vendor keys, moves the Debian and PGDG suites of the system's APT sources to Trixie and the recognised vendor entries to their Debian 13 feeds, and disables the stock testing line (originals kept in `apt-sources-bookworm/`, other sources untouched), refreshes the system lists, and removes the `policy-rc.d`. It prints `upgraded`.
7. The Launcher terminates and starts the distro (again without `start_env`), then runs `verify`. Exit 4 means a process still maps replaced files: restart again. `verify` requires Debian 13, a clean dpkg, no active Bookworm or rolling source and no vendor entry on its Debian 12 feed, no APT preferences other than the normalized stock pin file and the vendor pins, unchanged `/usr/local/cuda*` homes and links, `ensure_php_security --check` exit 0, every PHP 8.2 module present on 8.4 for each SAPI, `apache2ctl -t`, PG15 stopped, `disabled` and with its recorded identity, PG17 with its recorded identity, unchanged private configuration digests, each retained venv starting Python 3.11, the fixed CTranslate2 library importing and running in the LocalWhisper venv, the planned WSL DKMS override still in place, and the fence file still present. It then starts PG17 only on a private peer socket under `/var/lib/postgresql/.trixie-verify` with `listen_addresses=''` and autovacuum off, compares roles, role settings, database identities, extensions and the retained template's contents with the fence record, loads `vector` where installed, refreshes the collation version of C.UTF-8 databases (a catalog update that needs no connection to the database, so closed ones stay closed) and stops PG17. On success it records the dpkg digest and the new PG17 seal, sets phase `verified` and prints `verified`. **The fence stays**: `start_env`, `update.sh` and PG17 maintenance still refuse, `17/dwemer` stays `manual`, and no application can write. `verify` may be repeated while `verified`; each run checks everything again and records a fresh seal.
8. The Launcher durably records that it will no longer roll this upgrade back to the recovery copy automatically, and only then runs `release`. While the fence stands, `release` refuses (exit 3, nothing changed) when dpkg changed, PG17 runs or its seal changed since `verify`, or a closed database may still be open; run `verify` again. Otherwise it restores the `17/dwemer` start setting, removes the fence and only then sets phase `current`, and prints `current` with the writers that ran before under their Debian 13 names (`restart_services`, for example `php8.4-fpm` for `php8.2-fpm`). It then starts again what ran at the fence, under those names (`restore`, see below). The Launcher then starts the distro normally.

`release` is crash-idempotent. Each step checks before it acts and the phase changes last, so a crash at any point leaves `verified` and a rerun completes it: with the fence still present the checks run again; once the fence is gone writes may already have been admitted, so `release` only finishes (restores the start setting if needed, sets `current`). Once `current`, it only finishes a pending restore and otherwise changes nothing.

### Restoring what ran at the fence

When the fence lifts (`upgrade --cancel`, a `prepare` that defers after fencing, or `release`), Core journals a `restore` in the same write as the new phase: `17/dwemer` if PG17 served at the fence (`pg17_was_running`), and the writers that ran (`running`, under their Debian 13 names after `release`). It then starts each one that is stopped, PG17 first with `pg_ctlcluster 17 dwemer start`; a writer whose cluster did not start waits with it. It never stops anything, never starts PG15 and starts nothing at all (`problems`, restore left pending) when:

- the WSL registration (`WSL_DISTRO_NAME`) carries `-TrixieRecovery-`, the Launcher's proof copy or the failed disk it keeps after a restore;
- the PG17 journal is not `active` and cleaned, or `17/dwemer` is not its marked candidate or not the system identifier recorded at the fence;
- PG15 runs or its `start.conf` is not `disabled`, another server answers on the application socket, or a closed database may still be open.

The command's reply carries `restore` (`pending`, `pg17`, `services`, `running`, `failed`, `problems`) and `status` reports `restore_pending: true` while one is pending. A failed start, a refusal above or a crash after the phase changed never fails the command and never reopens the fence: rerun the same command (`upgrade --cancel` on a `cancelled` journal, `release` on a `current` one), which starts only what is still stopped, or start the distro normally. Neither suggests the recovery copy: once the fence has lifted, writes may have been admitted. A journal cancelled by an earlier Core records no restore and starts nothing; a normal start covers it.

No service starts and no port opens between steps 3 and 8. A Launcher must not run `update.sh`, Database Maintenance, server, mod or component actions while `status` is not `current`, `needed`, `deferred` or `not-needed`.

### Recovery states

| `status` state | Phase | Writes possible | Recovery copy | Launcher action |
|---|---|---|---|---|
| `fence-incomplete` | `fencing` | no | none yet | `upgrade --cancel`, then preflight again |
| `fenced` | `fenced` | no | being taken | finish step 4 and run step 5, or `upgrade --cancel` |
| `interrupted` | `upgrading` | no | valid | rerun step 5 with the same token; cancel only at step `lists` |
| `upgraded` | `upgraded` | no | valid | restart the distro, `verify` |
| `verified` | `verified` | no | valid; automatic rollback still allowed until the Launcher records otherwise | record no-auto-rollback, then `release` |
| `current` | `current` | yes | must not be restored automatically | start the distro normally |

A failed `verify` keeps phase `upgraded` (or `verified`), keeps the fence and lists its problems; restoring the recovery copy is still safe because nothing has written. Restoring after `release` would lose writes made on Debian 13.

## Interruption and retries

- Before dpkg runs (phases `fencing`, `fenced`, or `upgrading` at step `lists`), nothing on the system changed: `upgrade --cancel` restores the `17/dwemer` start setting, removes the fence and any `policy-rc.d` it installed, then starts again what ran at the fence (see [Restoring what ran at the fence](#restoring-what-ran-at-the-fence)). Network failures leave the phase `interrupted`; rerun step 5 with the same token.
- From step `dpkg` the helper and APT ignore SIGTERM, SIGHUP and SIGINT, so closing the Launcher cannot stop dpkg midway. A killed distro leaves `interrupted`: rerunning step 5 runs `dpkg --configure -a` and the same transaction from the downloaded packages, once more after a failure. Cancel is refused from here on; if the transaction cannot complete, restore the recovery copy from step 4.
- The post-upgrade steps are repeatable, and `verify` can be rerun until it passes. A failed `verify` keeps the fence and lists its problems. A private PG17 server left running by an interrupted `verify`, `prepare` or `cancel` in the same boot is recognised by the socket directory in its `postmaster.pid` and stopped first.
- `release` can be rerun after any interruption; see step 8.

## Not covered (deferred or open)

- Third-party APT sources other than GitHub CLI, PGDG and the exact vendor entries above defer. An installed `gh` is assumed to come from the configured GitHub CLI feed: one installed from Debian 12's own `gh` next to that feed is also upgraded to the feed's build. The private sources and pins this helper writes have been checked with Debian 13's APT against the live feed: the stock keyring verifies its `InRelease`, `gh` is the candidate, and its archive downloads with matching hashes. A full rehearsal with `gh` installed has not yet been run on a Bookworm image. Debian's own `nvidia-*` packages are upgraded. Only `nvidia-kernel-dkms` is handled for the WSL kernel (see [NVIDIA kernel module on the WSL kernel](#nvidia-kernel-module-on-the-wsl-kernel)); other DKMS packages are upgraded unchanged and would fail the same way if they build for the WSL kernel. The override covers only the planned module version and WSL kernel: a later `nvidia-kernel-dkms` with a new upstream version, or a new WSL kernel with `build/include`, builds for the WSL kernel again. Whether the 550 module compiles for the Debian kernels on Trixie's toolchain, and the override, have not been run on the reference laptop.
- Whether the Debian 13 vendor feeds carry the installed CUDA 12.8 or .NET 10 builds has not been rehearsed: installed components the feed does not carry keep their Debian 12 builds, and any solution that would remove them defers. The Debian 13 `packages-microsoft-prod` package's contents and the .NET 10 package names on the Debian 13 feed are checked by `ddistro_reign` at install time but have not been rehearsed; a mismatch refuses the build before anything is installed from the feed.
- Closed databases other than `template0` and the recognised retained template defer: inspecting them means opening them, which preflight does not do on the public server.
- A package installed from testing that Trixie does not ship under any version cannot be told apart from a Bullseye leftover; both are listed as `obsolete_kept`. One newer than Trixie's build defers.
- Manually installed so-bumped libraries without a declared successor, and manually installed packages Debian 13 dropped other than the four listed, still defer as `apt-removes-manual`.
- Unpackaged users of a replaced CUDA library outside venvs, `/usr/local` and `/opt` (for example under a home directory) are not searched.
- Core does not hash mod trees, models or component files; the recovery copy from step 4 covers them.
- Venvs with their own interpreters are checked only for system libraries their modules load and for executable-stack requests.
- Only the one stock CTranslate2 file is fixed. Reinstalling the same wheel later (for example by a LocalWhisper update) brings back the stock bits, which then fail to import on Debian 13. The speech probe runs only when a converted Whisper model is present, on silent features; it does not transcribe audio. Whether the cleared library works for every CTranslate2 code path (CUDA included) rests on the probe and the separate functional run on the reference laptop.
- The rehearsal, transaction and verification have not yet been run end to end on a real Bookworm image.
